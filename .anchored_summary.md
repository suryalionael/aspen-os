# Anchored Summary — Aspen OS

## Goal
Investigate production runtime performance to identify what keeps the RSC stream open for ~2s after TTFB.

## Constraints & Preferences
- Do NOT optimize anything — only investigate, profile, and report.
- No code modifications allowed.
- Use real production profiling (CDP, Node.js fetch streaming, Supabase REST queries).

## Reports Generated
1. **PRODUCTION_RUNTIME_TRACE.md** — Timeline, flame chart, top 20 CPU functions, JS coverage, bottleneck ranking.
2. **SHARED_BUNDLE_FORENSICS.md** (412 lines) — 409KB shared chunk content analysis, dependency tree, route usage matrix, dynamic import candidates.
3. **CPU_EXECUTION_BREAKDOWN.md** (178 lines) — CDP Performance metrics: only 77ms ScriptDuration (3.8%). 95.6% of gap is Network I/O. JS is NOT the bottleneck.
4. **RSC_STREAM_TRACE.md** (158 lines) — RSC streaming waterfall: 2-phase delivery, shell at +2ms (34KB), gap of ~1020ms while server computes DashboardContent (10 Supabase queries), content resolves at +1022ms (5KB).

## Key Findings
### Server Streaming
- Shell flushes in 2ms (layouts + sidebar data from cache + page heading + skeleton fallback) — 34.6KB
- Streaming gap: ~1020ms — server is inside Suspense boundary B:1 (DashboardContent)
- DashboardContent resolves at +1022ms — 5.2KB of RSC payload
- Stream ends ~3ms after content flush
- 2 Suspense boundaries: B:0 (sidebar data — resolves immediately, data is cached), B:1 (DashboardContent — 10+ queries, takes ~1020ms)
- 1 Client-only boundary: BAILOUT_TO_CLIENT_SIDE_RENDERING (component that can only render on the client)

### What the Server Does During the Gap
1. Batch 1 (8 parallel Supabase queries): tasks assigned, tasks due today, upcoming deadlines, project_favorites, all task IDs, notes, meetings
2. Merge legacy single-assignee + multi-assignee task lists
3. Batch 2 (2 parallel queries, depends on Batch 1 task IDs): task_activity last 10, workspace_members_with_email RPC
4. Render resolved React tree
5. Flush B:1 resolution chunk

### Supabase Query Latency (External)
Slowest query from external measurement: `task_activity (last 10)` at 215ms (most rows — 0). From Vercel's edge network, latencies would be 5-30ms per query. The streaming gap (1020ms) is dominated by Vercel cold start + server-side computation.

### CPU Execution (from CDP Performance.getMetrics)
- Total ScriptDuration: 77ms (3.8% of 2019ms critical path)
- Total TaskDuration: 146ms (7.2% of critical path)
- Total ProcessTime: 318ms
- **95.6% is Network I/O + idle** — waiting for the RSC stream to finish
- The 409KB shared chunk contributes negligible execution time (~77ms total for all JS)

## Stream Structure
- 7 network chunks across 2 distinct phases
- Phase 1 (shell): 5 chunks, 34.6KB, +2ms — DOCTYPE, CSS, scripts, sidebar data, page heading, fallback skeleton
- Phase 2 (content): 2 chunks, 5.2KB, +1022ms — DashboardContent grid cards, B:1 resolution callback

## Answer
The HTTP stream stays open because **`DashboardContent` (a Server Component inside Suspense boundary B:1) executes 10+ Supabase queries in 2 sequential batches and then renders the result**. The server cannot flush until all queries resolve and React renders. The primary cause of the ~1020ms delay is the time to execute these queries from Vercel's edge function, plus cold start overhead and React rendering.
